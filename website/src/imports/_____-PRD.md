## 2. 产品概述

### 2.1 产品定位

| 项目 | 内容 |
|------|------|
| 产品名称 | 城市猜猜猜 |
| Slogan | 一城一世界，一战见真章 |
| 一句话定位 | 基于地理知识的实时对战竞技类休闲益智游戏 |
| 产品类型 | 休闲益智类移动游戏 / 知识竞技类应用 |
| 核心差异化 | 13城市组合生成题目机制 + 实时抢答对战 + SVG地图点亮探索 |

### 2.2 目标用户画像

#### 2.2.1 主要用户群

| 维度 | 描述 |
|------|------|
| 年龄段 | 18-35岁为主，延伸至12-45岁 |
| 职业特征 | 学生、白领、公务员、教师 |
| 兴趣爱好 | 地理知识、 trivia 问答、竞技游戏、社交互动 |
| 使用场景 | 通勤地铁、午休时间、睡前放松、朋友聚会 |

#### 2.2.2 用户痛点与需求

| 痛点 | 需求 |
|------|------|
| 传统问答游戏缺乏竞技性 | 实时对战，抢答机制 |
| 地理知识学习枯燥 | 游戏化学习，地图探索 |
| 缺乏知识变现/成就感渠道 | 积分排名、勋章成就系统 |
| 碎片时间难以深度游戏 | 单局10题，3-5分钟完成 |

### 2.3 核心价值主张

**对用户的价值**：
- 知识学习：在娱乐中掌握地理知识
- 竞技乐趣：实时对战带来的紧张刺激
- 社交互动：好友对战、排行榜竞争

**对平台的价值**：
- 用户留存：每日打卡、成就收集驱动
- 社交裂变：好友邀请、对战分享
- 商业化潜力：广告、会员、内购

### 2.4 商业模式（概要）

| 盈利模式 | 说明 |
|----------|------|
| 广告变现 | 应用启动页广告、Banner广告（可选，以用户体验优先） |

### 2.5 产品愿景与发展路线

| 阶段 | 目标 |
|------|------|
| 短期（MVP） | 核心对战功能上线，验证产品市场契合度 |
| 中期（V2.0） | 完善社交体系，建立用户成长激励闭环 |
| 长期（V3.0+） | 打造地理知识竞技生态，拓展教育B端市场 |

| 功能 | 需求描述 |
|------|----------|
| 手机号注册/登录 | 支持手机号+验证码快速登录 |

**新手引导默认国家逻辑**：
- 根据用户IP地址自动定位所在国家

#### 3.2.2 用户资料

| 字段 | 规则 |
|------|------|
| 头像 | 系统预设30个头像供选择，不支持自定义上传 |
| 昵称 | 2-12字符，支持中文/英文/数字，无修改次数限制 |
| 个人签名 | 0-50字符，可选填 |
| 所在地区 | 选择国家+省份，影响省份排行榜归属 |
| 性别 | 男/女/保密，可选填 |

**用户信息修改审核流程**：

后台系统配置可开启/关闭审核功能：

| 字段 | 审核开关 | 审核消息通知 |
|------|----------|--------------|
| 头像 | 系统配置：头像审核开关 | 通过消息邮箱通知 |
| 昵称 | 系统配置：昵称审核开关 | 通过消息邮箱通知 |
| 个人签名 | 系统配置：签名审核开关 | 通过消息邮箱通知 |

**审核流程**：
- 字段修改后，如该字段审核开关开启，则进入审核队列
- 审核通过后生效，审核不通过保留原信息
- 审核结果通过「消息邮箱-系统通知」告知用户
- 审核时效：通常1-2小时

### 3.4 对战匹配模块

#### 3.4.1 匹配流程（简化版）

**核心原则**：简单直接，选择国家后即可匹配，题目类型客户端随机生成。

```
选择国家 → 点击匹配 → 匹配中
    ↓
匹配成功（真人）/ 分配AI（匹配不到真人）
    ↓
对战准备界面（3秒倒计时）
    ↓
进入对战
```

**匹配流程说明**：

| 步骤 | 说明 |
|------|------|
| 选择国家 | 在首页地图选择国家，或匹配页选择国家 |
| 发起匹配 | 点击「开始匹配」按钮 |
| 匹配中 | 系统按积分范围搜索真人对战对手 |
| 匹配结果 | 匹配到真人 → 进入真人对抗；未匹配到 → 自动分配AI对手 |
| 对战进行 | 10道题抢答对战 |

#### 3.4.2 积分范围匹配机制

**匹配逻辑**：

```
1. 用户发起匹配请求
   参数：国家、用户当前积分

2. 判断是否使用AI匹配
   如果用户积分 < 系统配置的「匹配最低积分」
   → 直接分配对应等级的AI对手

3. 积分范围匹配（正常流程）
   初始范围：用户积分 ± 系统配置的「匹配积分范围」
   查询匹配池中积分在此范围内的用户

4. 范围扩展机制
   如果初始范围内无匹配用户
   → 范围扩大一倍（如初始±100，扩展后±200）
   → 继续查询匹配池

   重复扩展，直到达到系统配置的「匹配拓展次数」上限

5. 匹配结果
   匹配到真人 → 进入真人对抗
   达到拓展次数仍未匹配到 → 分配对应等级的AI对手
```

**匹配参数说明**：

| 参数 | 说明 | 默认值（示例） |
|------|------|----------------|
| 匹配积分范围 | 初始搜索的积分上下浮动范围 | ±100 |
| 匹配拓展次数 | 范围扩展的最大次数 | 3次 |
| 匹配最低积分 | 低于此积分直接分配AI对手 | 500 |

**匹配示例**：

假设系统配置：匹配积分范围=±100，匹配拓展次数=3，匹配最低积分=500

| 用户积分 | 匹配过程 |
|----------|----------|
| 400 | 低于500，直接分配AI对手 |
| 1000 | 第1次：900-1100 → 无 → 第2次：800-1200 → 无 → 第3次：700-1300 → 无 → 分配AI |
| 1500 | 第1次：1400-1600 → 找到积分1480的用户 → 匹配成功 |

#### 3.4.3 AI 对手设计（不可辨识）

**核心原则**：AI对手完全模拟真人用户，用户无法辨识对手是AI。

**AI角色设计**：

| 等级 | 积分范围 | 正确率 | 答题时间 | 特点 |
|------|----------|--------|----------|------|
| 新手 | < 600 | 40-55% | 5-8秒 | 答题较慢，偶尔犯错 |
| 初级 | 600-900 | 50-65% | 4-7秒 | 正常水平 |
| 中级 | 900-1200 | 60-75% | 3-6秒 | 较有挑战 |
| 高级 | 1200-1500 | 70-85% | 2-5秒 | 高水平 |
| 专家 | > 1500 | 80-92% | 2-4秒 | 顶尖水平 |

**AI拟人化设计**：

| 设计点 | 说明 |
|--------|------|
| 昵称 | 使用常见中文昵称，如"小明同学"、"旅行者"、"知行合一"等 |
| 头像 | 从系统预设头像中随机选择 |
| 答题延迟 | 模拟真人思考时间，非瞬间作答 |
| 偶尔失误 | 偶尔"手滑"选错，增加真实感 |
| 情绪波动 | 连续答错后答题变慢（模拟紧张） |
| 答题时间分布 | 答题时间在合理范围内随机波动 |
| 积分显示 | AI显示的积分与其等级匹配 |

**用户无感知保障**：

- AI对手的昵称、头像与真人用户无差异
- AI的答题行为完全模拟真人
- 对战结束后AI对手显示在匹配记录中
- 用户无法通过任何标识识别AI对手

#### 3.4.4 对战流程与计分规则

**对战准备界面（3秒）**：
- 展示双方头像、昵称、当前积分
- 展示对战国家
- 倒计时3秒进入对战

**答题流程（10道题，抢答模式）**：

| 阶段 | 说明 |
|------|------|
| 题目展示 | 展示题目内容（文字/图片）+ 4个选项 |
| 题目类型 | 服务端生成13道题目，客户端展示 |
| 抢答计时 | 每题10秒倒计时，进度条显示 |
| 答题反馈 | 正确：绿色+粒子效果；错误：红色+抖动；超时：灰色 |
| 比分展示 | 顶部实时展示双方比分 |

**抢答机制**：

每道题双方同时作答，服务端根据以下规则判定先后：

| 场景 | 处理方式 |
|------|----------|
| 一方先答对 | 先答对者得分，另一方不得分不扣分 |
| 一方先答错 | 先答错者扣分，另一方仍可继续作答 |
| 双方同时提交 | 服务端按请求到达时间戳判定先后（毫秒级） |
| 双方同时答对 | 先到达者得分，后到达者不得分不扣分 |
| 双方同时答错 | 双方均扣分 |
| 双方均超时 | 双方均不得分不扣分 |

**抢答详细流程**：
```
1. 题目展示，10秒倒计时开始
2. 双方各自选择答案，提交至服务端
3. 服务端按请求时间戳排序，依次判定：

   情况A：用户A先提交
   - A答对 → A得分，B自动跳过（B不得分不扣分）
   - A答错 → A扣分，B仍可继续作答（剩余倒计时内）
     → B答对 → B得分
     → B答错 → B扣分
     → B超时 → B不得分不扣分

   情况B：双方同时提交（时间差 < 100ms视为同时）
   - 各自独立判定对错，分别计分

4. 判定完成后展示双方结果，进入下一题
```

**计分规则（基础分+连续答对奖励）**：

| 答题结果 | 本方答题得分 | 对方答题得分 | 说明 |
|----------|-------------|-------------|------|
| 抢答答对（先答对） | +2分 | 0分 | 对方跳过，不扣分 |
| 抢答答错（先答错） | -2分 | 待定 | 对方仍可作答 |
| 对方先答对后，自己跳过 | 0分 | 0分 | 被跳过，不扣分 |
| 对方先答错后，自己答对 | +2分 | -2分（对方已扣） | 正常计分 |
| 对方先答错后，自己答错 | -2分 | -2分（对方已扣） | 双方均扣分 |
| 对方先答错后，自己超时 | 0分 | -2分（对方已扣） | 自己不得分 |
| 双方同时答对 | 先到达者+2分 | 后到达者0分 | 按时间戳判定 |
| 双方同时答错 | -2分 | -2分 | 各自扣分 |
| 双方均超时 | 0分 | 0分 | 均不得分 |

**连续答对额外加分**：
- 连续答对第2题：额外+1分
- 连续答对第3题：额外+2分
- 连续答对第4题：额外+3分
- 以此类推，额外加分 = (连续次数-1) × 1分

**计分示例**：
```
用户A连续答对3题：
- 第1题：+2分
- 第2题：+2分 + 1分(连续奖励) = +3分
- 第3题：+2分 + 2分(连续奖励) = +4分
- 总计：+9分

对方B连续被扣分：
- 第1题：-2分
- 第2题：-2分 - 1分(连续惩罚) = -3分
- 第3题：-2分 - 2分(连续惩罚) = -4分
- 总计：-9分
```

**对战结束积分计算**：
对战结束后，按照双方答题总得分计算胜负：
- 答题总得分高者获胜
- 胜者积分增加 = 胜者答题得分 - 败者答题得分
- 败者积分扣除 = 胜者答题得分 - 败者答题得分（相同分差）

**对战结束积分计算示例**：
```
对战结束（10题全部完成）：
- 用户A答题总得分：16分
- 用户B答题总得分：4分
- 胜者：A（16分 > 4分）
- 胜者积分变动：+12分（16 - 4 = 12）
- 败者积分变动：-12分

或：

对战结束（提前结束）：
- 用户A答题总得分：12分（提前结束）
- 用户B答题总得分：2分
- 胜者：A（12分 > 2分）
- 胜者积分变动：+10分（12 - 2 = 10）
- 败者积分变动：-10分
```

**大比分领先提前结束机制**：

| 条件 | 处理 |
|------|------|
| 双方分差达到系统配置值 | 提前结束对战，高分者获胜 |
| 默认分差阈值 | 10分（系统可配置） |

**提前结束示例**：
```
第6题结束后：
- 用户A得分：12分
- 用户B得分：2分
- 分差：10分（达到阈值）
- 结果：对战提前结束，用户A获胜
```

**加赛机制**：
- 10题后比分相同，触发加赛，放出最后3题
- 加赛规则同正赛（计分、连续答对奖励等）
- 加赛3题后比分仍相同，按答题速度判定胜负（累计答题时间短者获胜）

**对战结束界面**：
- 展示胜负结果、最终比分
- 展示积分变动（+/-）
- 操作按钮：再来一局、返回首页、分享战绩



### 3.5 题库模块

#### 3.5.1 题目生成机制

**核心逻辑**：
服务端随机获取13个城市（最少覆盖4个省份），随机组合生成13道完整题目后传送给客户端。

**数据流程**：
```
1. 客户端请求：GET /api/match/questions
   参数：country_id

2. 服务端处理：
   Step 1: 从该国家城市库中随机选取13个城市
           - 约束条件：13个城市至少来自4个不同省份
           - 省份分布尽量均匀，避免集中在1-2个省份
   
   Step 2: 为13个城市随机组合生成13道题目
           - 为每个城市随机选择一种题目类型
           - 生成完整的题目内容（题干、选项、正确答案）
           - 确保题目类型分布相对均衡
   
   Step 3: 保存匹配答题记录模板
           - 记录match_id、13道题目信息
           - 便于后续保存答题结果
   
   Step 4: 返回13道完整题目给客户端

3. 服务端返回数据结构：
   {
     "match_id": "xxx",
     "questions": [
       {
         "question_id": "q1",
         "question_type": "city_to_province",

         "question_text": "西湖龙井产自哪个城市？",

   - 直接接收13道完整题目
   - 展示题目进行答题
   - 答题结果提交给服务端保存
```

**省份覆盖约束**：

| 约束 | 说明 |
|------|------|
| 最少省份数 | 13个城市至少来自4个不同省份 |
| 分布均衡 | 尽量每个省份2-4个城市，避免某省份过多 |
| 随机性 | 每次对战随机选取，确保重复可玩性 |

**题目类型分布规则**：
- 7种题目类型随机分配
- 同一题目类型可出现多次，但不超过3次
- 确保题目类型分布相对均衡

**优势**：
- 服务端生成完整题目，便于保存匹配答题记录
- 客户端无需处理题目生成逻辑，简化客户端实现
- 题目数据完整，便于后续数据分析和统计

#### 3.5.2 题目类型定义

| 题目类型 | 题目形式 | 选项生成逻辑 | 优先级 |
|----------|----------|--------------|--------|

| 古名猜现代城市 | "古称'临安'的现代城市是？" | 正确答案+3个其他城市 | P0 |

**选项生成规则**：
- 正确答案固定为当前城市
- 3个干扰项从同国家其他城市随机选取

- 避免明显错误的选项（如问中国城市出现纽约）

#### 3.5.3 城市数据结构

```typescript
interface City {
  id: string;                    // 城市唯一ID
  name: string;                  // 城市名称
  alias: string[];               // 城市别名（如"羊城"）
  ancient_names: string[];       // 城市古名（如"临安"、"钱塘"）
  country_id: string;            // 所属国家ID
  country: Country;              // 所属国家信息
  province_id: string;           // 所属省份ID
  province_name: string;         // 省份名称
  coordinates: {                 // 经纬度坐标
    lat: number;
    lng: number;
  };
  events: CityEvent[];           // 城市事件列表
  titles: string[];              // 城市称号列表
  specialties: Specialty[];      // 特产列表
  landmarks: Landmark[];         // 标志建筑列表
  resources: Resource[];         // 其他资源列表（用于根据资源猜城市/省份）
}

interface Country {
  id: string;                    // 国家唯一ID
  name: string;                  // 国家名称
  code: string;                  // 国家代码（如CN、US、JP）
  flag_image: string;            // 国旗图片URL
}

interface CityEvent {
  id: string;
  title: string;                 // 事件标题
  description: string;           // 事件描述
  year: string;                  // 发生年份
  type: 'historical' | 'modern'; // 历史事件/现代事件
}

interface Specialty {
  id: string;
  name: string;                  // 特产名称
  description: string;           // 特产描述
  image: string;                 // 特产图片URL
}

interface Landmark {
  id: string;
  name: string;                  // 建筑名称
  description: string;           // 建筑描述
  images: string[];              // 多张图片URL
}

interface Resource {
  id: string;
  name: string;                  // 资源名称
  type: string;                  // 资源类型（如"美食"、"民俗"、"自然景观"、"非遗"等）
  description: string;           // 资源描述
  image: string;                 // 资源图片URL
}
```

**数据结构说明**：

| 字段变更 | 说明 |
|----------|------|
| alias | 仅保留城市别名（如"羊城"、"蓉城"），不再包含古名 |
| ancient_names | 新增，独立存储城市古名（如"临安"、"钱塘"） |
| country | 新增，关联国家信息对象（含国旗图片） |
| flag_image | 从City中移除，移至Country对象 |
| difficulty | 已移除，不再需要题目难度系数 |
| resources | 新增，其他资源列表，用于扩展题目类型 |

**文件处理流程**：

```
1. 文件上传
   - 客户端选择文件 → 前端校验格式/大小 → 上传至服务端
   - 服务端二次校验 → 生成唯一文件名 → 存储至对象存储（OSS/S3）
   - 返回文件URL → 客户端展示预览

2. 图片处理
   - 生成缩略图（头像：100x100, 200x200）
   - 图片压缩（质量85%，控制文件大小）
   - 水印处理（可选，后台配置开关）

3. 审核流程（用户头像）
   - 上传后进入待审核状态
   - 审核通过：更新user.avatar_url，通知用户
   - 审核拒绝：保留原头像，通知用户原因

4. 文件清理
   - 定期清理未引用的临时文件
   - 删除用户时保留头像7天（防误删）
```

**存储方案**：
- 生产环境：阿里云OSS / AWS S3 + CDN加速
- 开发环境：本地存储或MinIO

## 6. 积分系统与匹配机制

### 6.1 积分系统概述

本应用采用简单的积分系统，积分是唯一的实力标识。

**核心原则**：
- 只有积分，没有段位
- 积分反映用户真实水平
- 匹配基于积分范围，非ELO算法

### 6.2 积分规则

| 参数 | 值 | 说明 |
|------|-----|------|
| 初始积分 | 1000 | 新用户起始分数 |
| 最低积分 | 100 | 防止负分 |
| 积分上限 | 无上限 | 顶级玩家可持续增长 |

**对战积分计算规则**：
详见3.4.4节对战流程与计分规则。核心规则：
- 答题基础分：答对+2分（对方-2分），答错-2分（对方+2分）
- 连续答对奖励：额外加分 = (连续次数-1) × 1分
- 对战结束积分变动 = 胜者答题得分 - 败者答题得分

**防连败保护**：
- 连续失败5场后，失败扣分减半（向下取整）
- 连胜3场后恢复正常扣分规则

### 6.3 积分范围匹配机制

**匹配逻辑**：

```
1. 用户发起匹配请求
   参数：国家、用户当前积分

2. 判断是否使用AI匹配
   如果用户积分 < 系统配置的「匹配最低积分」
   → 直接分配对应等级的AI对手

3. 积分范围匹配（正常流程）
   初始范围：用户积分 ± 系统配置的「匹配积分范围」
   查询匹配池中积分在此范围内的用户

4. 范围扩展机制
   如果初始范围内无匹配用户
   → 范围扩大一倍
   → 继续查询匹配池

   重复扩展，直到达到系统配置的「匹配拓展次数」上限

5. 匹配结果
   匹配到真人 → 进入真人对抗
   达到拓展次数仍未匹配到 → 分配对应等级的AI对手
```

**匹配参数说明**：

| 参数 | 说明 | 默认值（示例） |
|------|------|----------------|
| 匹配积分范围 | 初始搜索的积分上下浮动范围 | ±100 |
| 匹配拓展次数 | 范围扩展的最大次数 | 3次 |
| 匹配最低积分 | 低于此积分直接分配AI对手 | 500 |

**匹配示例**：

假设系统配置：匹配积分范围=±100，匹配拓展次数=3，匹配最低积分=500

| 用户积分 | 匹配过程 |
|----------|----------|
| 400 | 低于500，直接分配AI对手 |
| 1000 | 第1次：900-1100 → 无 → 第2次：800-1200 → 无 → 第3次：700-1300 → 无 → 分配AI |
| 1500 | 第1次：1400-1600 → 找到积分1480的用户 → 匹配成功 |

### 6.4 对战参数配置

| 参数 | 说明 | 默认值 |
|------|------|--------|
| 大比分领先阈值 | 双方分差达到此值时提前结束对战 | 10分 |
| 对战计分基础分 | 答对/答错的基础分值 | 2分 |
| 连续答对奖励倍数 | 额外加分 = (连续次数-1) × 此倍数 | 1分 |

### 6.5 特殊场景处理

| 场景 | 处理方案 |
|------|----------|
| 玩家中途退出 | 判负，按正常失败扣分；对手按胜利加分 |
| 平局（加赛3题后仍相同） | 按累计答题时间判定胜负，时间短者获胜 |
| 新手保护 | 前5场优先匹配积分相近的新手 |
| AI对战 | AI使用虚拟积分（与用户积分等级匹配） |

### 6.6 AI对手等级对照

| AI等级 | 积分范围 | 正确率 | 答题时间 |
|--------|----------|--------|----------|
| 新手 | < 600 | 40-55% | 5-8秒 |
| 初级 | 600-900 | 50-65% | 4-7秒 |
| 中级 | 900-1200 | 60-75% | 3-6秒 |
| 高级 | 1200-1500 | 70-85% | 2-5秒 |
| 专家 | > 1500 | 80-92% | 2-4秒 |

## 9. 开发考虑问题

### 9.1 抢答并发处理

| 问题 | 解决方案 |
|------|----------|
| 双方同时提交答案 | 服务端按请求时间戳（毫秒级）判定先后，时间差<100ms视为同时 |
| 网络延迟导致不公平 | 服务端记录请求到达时间，非客户端发送时间 |
| 先答错后对方作答 | 先答错者立即扣分，对方在剩余倒计时内仍可作答 |
| 答案泄露风险 | 双方答案均在对方提交或超时后才返回，防止截取答案 |
| WebSocket断连 | 断连后自动判负，记录断连时间点，保留已有答题记录 |

### 9.2 AI对手实时性

| 问题 | 解决方案 |
|------|----------|
| AI答题时间模拟 | AI答案延迟生成，模拟真人思考时间（2-8秒随机） |
| AI不可辨识 | AI使用与真人相同的用户表结构（is_auto=1），昵称头像从预设库随机选取 |
| AI答题逻辑 | 根据AI等级设定正确率，随机选择答题时间，偶尔"手滑"选错 |
| AI断连模拟 | AI不会断连，但偶尔模拟"网络波动"延迟作答 |

### 9.3 数据一致性

| 问题 | 解决方案 |
|------|----------|
| 对战中断（网络/退出） | 中断方判负，已完成的答题记录保留，积分正常结算 |
| 重复提交答案 | 服务端对每题每用户只接受第一次提交，后续提交忽略 |
| 积分计算准确性 | 对战结束后统一结算积分，使用数据库事务保证一致性 |
| 匹配状态同步 | 使用Redis维护匹配池状态，匹配成功后立即移除 |

### 9.4 性能优化

| 问题 | 解决方案 |
|------|----------|
| 高并发匹配 | Redis有序集合维护匹配池，按积分范围快速查询 |
| 题目预加载 | 匹配成功后立即生成题目，答题前完成加载 |
| 实时比分同步 | WebSocket双向通信，答题结果实时推送 |
| 排行榜查询 | Redis缓存排行榜数据，定时刷新（每5分钟） |
| 地图SVG加载 | 按国家懒加载SVG地图，首屏只加载当前国家 |

### 9.5 安全问题

| 问题 | 解决方案 |
|------|----------|
| 答案作弊（抓包/改包） | 答案校验在服务端完成，客户端只传递选项ID |
| AI对手辨识 | AI用户数据与真人完全一致，接口不暴露is_auto字段 |
| 刷积分 | 接口限流（每用户每分钟最多发起3次匹配），异常积分波动监控 |
| 用户资料审核 | 敏感字段修改需审核，审核通过后才生效 |
| 数据库ID安全 | 使用UUID，避免自增ID被猜测遍历 |

### 9.6 多平台兼容

| 问题 | 解决方案 |
|------|----------|
| iOS/Android适配 | Flutter跨平台开发，一套代码双端运行 |
| 不同屏幕尺寸 | 响应式布局，适配手机/平板 |
| 弱网环境 | 答题结果本地缓存，网络恢复后同步 |
| 推送通知 | 集成Firebase（海外）+ 极光推送（国内） |

### 9.7 运维监控

| 问题 | 解决方案 |
|------|----------|
| 服务可用性 | 核心服务部署多实例，负载均衡 |
| 异常告警 | 对战超时、匹配失败、AI异常等场景触发告警 |
| 数据备份 | 数据库每日自动备份，保留30天 |
| 日志管理 | 操作日志写入Elasticsearch，便于查询分析 |
| 热更新 | 后台系统配置支持运行时修改，无需重启服务 |

### 9.8 扩展性设计

| 问题 | 解决方案 |
|------|----------|
| 新增题目类型 | 题目类型使用枚举+策略模式，新增类型只需添加策略类 |
| 新增国家支持 | 国家数据配置化，新增国家只需录入数据+上传SVG地图 |
| 匹配算法调整 | 匹配参数通过system_config表配置，无需改代码 |
| AI等级扩展 | AI等级参数配置化，支持动态调整 |

### 9.9 WebSocket通信设计

**WebSocket连接管理**：

| 连接类型 | 说明 | 认证方式 |
|----------|------|----------|
| 用户连接 | 每个登录用户建立一条WS连接 | JWT Token |
| 对战房间连接 | 匹配成功后进入对战房间 | Room ID + Token |
| 心跳机制 | 每30秒发送ping/pong心跳 | 服务端主动ping |
| 重连机制 | 断线后自动重连，最多5次 | 指数退避策略 |

**消息协议设计**：

```typescript
// 基础消息格式
interface WSMessage {
  type: string;      // 消息类型
  timestamp: number; // 发送时间戳（毫秒）
  data: any;         // 消息数据
}

// 1. 匹配相关消息
// 客户端 -> 服务端：发起匹配
{
  type: 'match:start',
  data: {
    country_id: string,  // 选择的国家
    user_score: number   // 当前积分
  }
}

// 服务端 -> 客户端：匹配成功
{
  type: 'match:success',
  data: {
    match_id: string,      // 对战ID
    room_id: string,       // 房间ID
    opponent: {            // 对手信息
      id: string,
      nickname: string,
      avatar_url: string,
      score: number
    },
    questions: Question[], // 13道题目
    countdown: 3           // 准备倒计时（秒）
  }
}

// 服务端 -> 客户端：匹配失败（超时）
{
  type: 'match:timeout',
  data: {
    reason: 'timeout',
    message: '匹配超时，已为您分配AI对手'
  }
}

// 2. 对战答题消息
// 服务端 -> 客户端：开始答题
{
  type: 'battle:start',
  data: {
    question_index: 0,  // 当前题号（0-9）
    question: Question, // 题目内容
    time_limit: 10      // 答题时间（秒）
  }
}

// 服务端 -> 客户端：倒计时同步
{
  type: 'battle:countdown',
  data: {
    question_index: number,
    remaining_time: number  // 剩余秒数
  }
}

// 客户端 -> 服务端：提交答案
{
  type: 'battle:answer',
  data: {
    match_id: string,
    question_index: number,
    option_id: string,      // 选项ID（A/B/C/D）
    submit_time: number     // 提交时间戳（毫秒）
  }
}

// 服务端 -> 客户端：答题结果（双方均提交或超时后推送）
{
  type: 'battle:result',
  data: {
    question_index: number,
    results: [
      {
        user_id: string,
        option_id: string,
        is_correct: boolean,
        response_time: number,  // 答题用时（毫秒）
        score_change: number    // 本题得分变化
      }
    ],
    scores: {  // 当前总分
      [user_id: string]: number
    },
    correct_option: string  // 正确答案
  }
}

// 3. 大比分领先提前结束
{
  type: 'battle:early_end',
  data: {
    reason: 'lead_threshold',
    winner_id: string,
    final_scores: {
      [user_id: string]: number
    }
  }
}

// 4. 加赛消息
{
  type: 'battle:extra',
  data: {
    extra_questions: Question[],  // 3道加赛题
    reason: 'tie'                 // 10题后平局
  }
}

// 5. 对战结束
{
  type: 'battle:end',
  data: {
    match_id: string,
    winner_id: string | null,  // null表示平局（按答题时间判定后）
    final_scores: {
      [user_id: string]: number
    },
    score_changes: {  // 积分变动
      [user_id: string]: number
    },
    statistics: {     // 对战统计
      correct_count: { [user_id: string]: number },
      avg_response_time: { [user_id: string]: number }
    }
  }
}

// 6. 用户消息通知
{
  type: 'message:new',
  data: {
    message_id: string,
    sender_type: 0 | 1 | 2,  // 0系统 1官方 2好友
    title: string,
    content: string,
    created_at: string
  }
}

// 7. 异常处理消息
// 对方断开连接
{
  type: 'error:opponent_disconnect',
  data: {
    opponent_id: string,
    message: '对手已断开连接'
  }
}

// 自己断开连接（重连时）
{
  type: 'error:self_disconnect',
  data: {
    message: '连接已断开，正在重连...',
    reconnect_count: number  // 当前重连次数
  }
}

// 对战异常终止
{
  type: 'error:battle_abort',
  data: {
    reason: 'server_error' | 'timeout' | 'invalid_state',
    message: string
  }
}
```

**WebSocket状态机**：

```
用户连接状态：
[已连接] --发起匹配--> [匹配中] --匹配成功--> [对战准备]
   |                      |
   |                      └--匹配超时--> [匹配AI]
   └--断开连接--> [离线]

对战状态：
[对战准备] --倒计时结束--> [答题中] --10题完成--> [判断是否加赛]
   |                           |
   |                           └--大比分领先--> [对战结束]
   └--对方断开--> [对战结束]

[判断是否加赛] --平局--> [加赛答题] --3题完成--> [对战结束]
              --有胜者--> [对战结束]
```

**异常处理流程**：

| 异常场景 | 处理方案 | 消息通知 |
|----------|----------|----------|
| 用户断连（对战前） | 取消匹配，用户回到空闲状态 | match:cancelled |
| 用户断连（对战中） | 判负，对手获胜，保留已答题记录 | battle:end（对手获胜） |
| 对手断连 | 本方获胜，积分正常结算 | battle:end（本方获胜） |
| 服务端异常 | 对战终止，双方不扣积分，记录异常日志 | error:battle_abort |
| 网络抖动（<3秒） | 自动重连，恢复对战状态 | 无（静默恢复） |
| 网络抖动（>3秒） | 判负，按断连处理 | battle:end |
| 重复提交答案 | 只接受第一次提交，后续忽略 | 无 |
| 超时未提交 | 该题不得分，进入下一题 | battle:result（超时标记） |
